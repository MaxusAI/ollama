# MaxusAI/ollama#455: does llama.cpp#29953's y-tile guard compile, and fire, under hipcc?
# mmq-29953-guard-verify-hip.sh on llama.cpp 3070d927f with mmq-29953-y-tile-guard.patch as #455 published it (blob
# 729f22c2): mmq.cu compiled for gfx1151 with -ferror-limit=0 and no ccache, each build scored by why it failed. Four
# runs: the patch as published and VARIANT=instantiate, each with CMake's own compile command and with the minimal
# hipcc command. Host: amd-server, the same host and toolchain as host-profile_mmq-successor-gfx1151.json (#450).
#
# Build 5 differs from the nvcc script's on purpose. #455 asked for rdna3_5's first 256-thread config at 192 threads.
# That config has J = 64, and 64*36 ints = 12*192, so GGML_PAD's bit mask happens to round correctly: there is
# nothing to catch. At 192 threads the bit mask is short only for J = 8, 56, 72 and 120, and rdna3_5 uses J = 16 to
# 128 in steps of 16, so no rdna3_5 config can fire at 192. Build 5a is #455's mutation and must compile; build 5b
# moves the same config to 160 threads, where the bit mask gives 9216 B and the load reads 15*160 ints = 9600 B;
# build 5c is the nvcc script's build 5, blackwell's first 256-thread config (J = 8) at 192 threads.

Builds 3, 4, 5b and 5c fail for the right reason, but score WRONG-REASON: clang reports one failing type per table,
then a knock-on error at the same line. The first pair from build 3; every failing table gives the same pair:
    ggml/src/ggml-cuda/mmq.cu:530:1: error: static assertion failed due to requirement 'ggml_cuda_mmq_y_tile_ok_pascal_older(42)': MMQ: the y tile helper is smaller than the y load for a config in the pascal_older table
    ggml/src/ggml-cuda/mmq.cu:530:1: error: static assertion expression is not an integral constant expression
The knock-on is the outer static_assert(ggml_cuda_mmq_y_tile_all_<table>(...) > 0, ""): once a per-type assertion
fails, that function's instantiation is invalid, so the call is not a constant expression. In runs 1 and 2, all 44
knock-on errors sit on a line where the guard failed, and no log has a "maximum step limit" note. But the words are
the ones clang prints when it hits -fconstexpr-steps.

VARIANT=instantiate replaces the function template and the outer static_assert
    template <int... ts> static constexpr size_t ggml_cuda_mmq_y_tile_all_##TABLE(std::integer_sequence<int, ts...>) {
        return (sizeof(ggml_cuda_mmq_y_tile_guard_##TABLE<ts>) + ... + 0);
    }
    static_assert(ggml_cuda_mmq_y_tile_all_##TABLE(std::make_integer_sequence<int, GGML_TYPE_COUNT>()) > 0, "");
with an explicitly instantiated class that inherits every per-type guard, so only the per-type assertions are
constant-evaluated.

== object code across runs
The patch as published vs VARIANT=instantiate, build 2, both compiled in one worktree to one output name with run 1's
CMake command: byte-identical, 166400 B. Objects from different runs are not, because each run has its own worktree
path: a -instantiate run's is 12 characters longer, which adds 24 B to .rodata.str1.1 (two __FILE__ strings; 166424
and 165336 B above) and changes __hip_cuid_*, which clang hashes from the file path and the command line. Their host
disassembly is identical.
