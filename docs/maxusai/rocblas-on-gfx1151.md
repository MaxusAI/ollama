# rocBLAS on gfx1151: what reaches it, and whether a better kernel exists

**Question this answers.** After the MMQ vs hipBLAS A/B, I wrote that rocBLAS
was worth investigating for "alternative more optimized kernels". This is that
investigation. Short answer: the two runtime routes are closed, the current
configuration is already the fast one by a factor of two, and the remaining
opportunity is not in rocBLAS's kernel selection but in whether these GEMMs
need to reach rocBLAS at all.

**Measured on** gfx1151 (Ryzen AI Max 395), build `0.34.2-dynres-f67b1aef`,
ROCm 7.2.4. Noise floor for throughput on this host is +-0.4%.

## Why these GEMMs reach rocBLAS at all

Not because `should_use_mmq` chose it. They never reach that function. The
first branch of `ggml_cuda_mul_mat` short-circuits:

```c
if (bad_padding_clear || src1->type != GGML_TYPE_F32 || dst->type != GGML_TYPE_F32) {
    ggml_cuda_mul_mat_cublas(ctx, src0, src1, dst);
    return;   // bypasses mmvf, mmf, mmvq and mmq entirely
}
```

Every captured call has `--d_type f16_r`, so every one of them takes this exit.

This corrects a claim worth stating plainly, because it changes how the earlier
A/B should be read: `GGML_CUDA_FORCE_CUBLAS` only changes what
`should_use_mmq` returns, so it **cannot move a single one of these GEMMs**.
They were on rocBLAS in both arms. That is why dense `gemma4:31b` measured
+2.1% in that A/B rather than showing an MMQ win -- a large share of its
prefill never had a choice of path. The A/B remains valid for what it measured;
it just never covered this.

## The two runtime routes, measured

Both are environment variables, so both were testable without a rebuild.
Three cold repeats each on `gemma4:31b-it-q4_K_M`, one per distinct image, with
the first request after server start discarded as `cold_start`.

| arm | document | finetext | chart | vs baseline |
|---|---|---|---|---|
| baseline | 155.1 | 154.9 | 153.3 | — |
| `ROCBLAS_USE_HIPBLASLT=1` | 153.7 | 153.7 | 152.4 | **-0.8%** |
| `GGML_CUDA_CUBLAS_COMPUTE_TYPE=f32` | 79.6 | 79.7 | 79.6 | **-48.6%** |

(prefill tok/s. Each rep uses a different image so every measurement is cold --
an earlier version of this probe reused one image and varied only the text,
which let the image prefix hit the KV cache and produced a 16x fake speedup.)

### hipBLASLt: closed, and not for a code reason

upstream llama.cpp notes hipBLASLt "performs better" than rocBLAS/Tensile on
CDNA3. On gfx1151 the knob does nothing measurable (-0.8%, barely outside the
noise floor and in the wrong direction). The reason is packaging, not
architecture:

| image | `libhipblaslt.so` | gfx1151 kernel files |
|---|---|---|
| `0.34.2-rocm724` (production) | present, 8.9 MB | **0** |
| `rocm10-gfx1151-probe` | present | **0** |

The shared object references `gfx1151` and `TensileLibrary_*_gfx1151`, but
neither image ships a `hipblaslt/library` directory, so there is nothing to
dispatch to. Revisiting this means shipping hipBLASLt Tensile kernels for
gfx1151, not flipping a flag.

### Compute type: already the fast one, by 2x

Every captured call runs `--compute_type f16_r` (FP16 accumulate). Forcing FP32
accumulate **halves prefill** (-48.6%, and remarkably tight: 79.6 / 79.7 / 79.6).
That ratio is what RDNA3.5 WMMA predicts for fp32-accumulate against
fp16-accumulate, so the default is not an accident and there is no headroom to
recover by changing it.

The open half of that question is accuracy: FP32 accumulate is the *more*
accurate option, so the 2x is only free if scores are unchanged. That is a
separate suite run, tracked below.

## What this rules out

- **Not** "swap in a better rocBLAS kernel via a runtime knob." Both knobs are
  either inert (hipBLASLt) or strictly worse (compute type).
- **Not** an upstream PR on the Q4_K `default: return true` threshold. The A/B
  measured that path at -0.1% on dense `qwen3.8:27b`; there is no win there.

## What remains open

1. **Accuracy under FP32 accumulate.** Does the 2x cost anything on fine text
   or bbox IoU? Suite run comparing `scores_cf32_*` against `scores_mmq_*`.
2. **Whether these GEMMs need rocBLAS at all.** The bailout triggers on
   `dst->type != F32`. An F16-output path through mmf would skip rocBLAS
   entirely for the tower shapes. That is an upstream design question, and the
   one place real headroom might be.
3. **hipBLASLt kernels for gfx1151**, if a future ROCm ships them.

## Regression sentinel

This is the artifact to keep. If prefill on this host ever halves, check
`compute_type` before anything else -- a change to the selection logic in
`ggml_cuda_mul_mat_cublas` reproduces exactly the -48.6% measured above. See
`rocm-regression-triage.md` for the surrounding procedure.
